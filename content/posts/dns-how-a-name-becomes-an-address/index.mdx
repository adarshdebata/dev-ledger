**You use it every day. But do you actually know what happens underneath?** In the [last post](/posts/one-request-seven-stops/), one bar in Chrome's Timing tab was called **DNS Lookup**. It took 118 ms, and it happened before the browser could even open a connection.

This post opens that bar up. Who answers the question "where is `api.example.com`?", why does the answer get copied everywhere, and what happens when one of those copies is wrong?

## What you see

You almost never see DNS when it works. You see it when it doesn't, and it rarely says its own name:

- A site opens on your phone's mobile data, but not on your Wi-Fi.
- You moved a site to a new server. Some people see the new one, some still see the old one, hours later.
- Chrome says **This site can't be reached**, and the console says:

<DevTools console={[{ level: "error", text: "Failed to load resource: net::ERR_NAME_NOT_RESOLVED" }]} />

All three are DNS. Before reading on, try this one:

Nothing gets "sent" anywhere. Answers are **copied and cached** along the way, and each copy is kept until its timer runs out. Your second friend is reading an old copy. The rest of this post is about who keeps those copies, and for how long.
</Predict>

## What's underneath

### Why can't the browser just use the name?

Because the internet doesn't deliver to names. It delivers to addresses. `api.example.com` is for people; the network needs an <Term id="ip-address">IP address</Term> like `203.0.113.10`. <Term id="dns">DNS</Term> is the system that turns one into the other, and it does it before every new connection.

### Who answers, in order

1. **The browser** checks its own small cache first.
2. **Your computer** checks its cache, and before that, a file called the <Term id="hosts-file">hosts file</Term>. A line in that file beats everything else.
3. **The resolver** does the real work. It's usually run by your internet provider, unless you've chosen a public one such as `8.8.8.8` (Google) or `1.1.1.1` (Cloudflare). It also keeps the biggest cache, shared by everyone who uses it.
4. If the resolver has no copy, it walks down from the top: a <Term id="root-server">root server</Term> says who handles `.com`, a <Term id="tld">.com server</Term> says who handles `example.com`, and finally the <Term id="authoritative-server">authoritative name server</Term> gives the real answer.

There are 13 root server names, `a.root-servers.net` to `m.root-servers.net`, and each one is really many machines spread around the world. But here's the surprising part: **your resolver almost never asks them.** We asked a root server directly: its answer about who handles `.com` came with a timer of 172,800 seconds. That's **48 hours**. Once a resolver has that answer, it doesn't need the root again for two days.

### Why it's fast: every step keeps a copy

Every answer comes with a <Term id="ttl">TTL</Term>, a "time to live" in seconds. It tells everyone along the way: *you may keep this copy for this long before asking again.* When we looked up `example.com`, its addresses came with a TTL of 300, so five minutes.

That's why the trip in the animation is usually short. Someone using your resolver probably asked for a popular name a minute ago, so the resolver answers from its copy in one round trip. If you asked yourself a few seconds ago, your own computer answers in about a millisecond, and DevTools shows a tiny DNS bar, or none at all.

<Callout type="insight" title="The TTL that jumps around">
You might expect to watch the TTL count down neatly: 300, then 295, then 290. We asked `1.1.1.1` for `example.com` three times in nine seconds and got **300, 231 and 36**. Big public resolvers are many machines behind one address, and each one keeps its own copy with its own countdown. The TTL you get back is just how long *that* machine's copy has left.
</Callout>

### What a DNS answer actually contains

A name usually has a few kinds of record:

- An <Term id="a-record">A record</Term> gives an IPv4 address, and an **AAAA** record an IPv6 address.
- A <Term id="cname">CNAME</Term> says "this name is really that other name", so the resolver goes on to look that one up.
- **NS** records say which servers are authoritative for a domain. These are the ones the root and `.com` hand out.

And one name can have **several addresses**. When we asked for `example.com`, we got two IPv4 addresses and one IPv6 address back. Browsers can try another address if one doesn't answer.

### "No" is cached too

When a name doesn't exist, the answer is <Term id="nxdomain">NXDOMAIN</Term>: no such name. That answer gets cached as well, which surprises people. We asked for a made-up name under `example.com`, and the "no" came with instructions to remember it for up to **1,800 seconds**, half an hour.

## What breaks

| What you see | Usual cause | How to check |
| --- | --- | --- |
| `net::ERR_NAME_NOT_RESOLVED` | A typo, an expired domain, or a record that doesn't exist yet | `nslookup` the name with a trailing dot (see the field notes) |
| Works on one network but not another | The two resolvers give different answers | Ask both resolvers the same question |
| Some people still see the old server after a move | Caches still hold the old answer until its TTL runs out | Read the TTL; lower it before the next move |
| A name only works on the office network or a VPN | The internal resolver knows names the public internet doesn't | Ask the internal and a public resolver |
| Only your computer sees a strange address | A forgotten line in your hosts file | Open the hosts file |
| A long **DNS Lookup** bar | A slow or distant resolver, or a name nobody nearby has asked for | Compare with a different resolver |
| `nslookup` says one thing, the browser another | The search-suffix trap, or a cached copy in one of them | Add a trailing dot; clear the browser's cache |

<Callout type="story" title="It happened to me">
A short link wouldn't open for me. The name was resolving fine, but my internet provider's DNS was handing out an address that was dead for that link shortener's domain. Asking Google's public resolver, `8.8.8.8`, directly gave a different address, one that worked. Nothing was wrong with the link, the browser or my computer. One resolver's answer was simply wrong.
</Callout>

That's the **A resolver that lies** scenario in the animation. Resolvers can be wrong by accident, like that one, and some are wrong on purpose: certain networks answer for names that don't exist, sending you to a search page or a "blocked" page instead of an error. Either way the lesson is the same. **When something works on one network and not another, compare what each resolver says before you blame anything else.**

## Field notes: debugging DNS

<Steps>
<Step title="Ask the question yourself, with a trailing dot">
`nslookup` is on every computer. But on Windows it has a trap: it adds your computer's <Term id="search-suffix">DNS search suffix</Term> to the name first. We hit this ourselves on a laptop with a company suffix: `nslookup example.com` returned the address of `example.com.<company-suffix>`, a completely different machine. Here's the shape of it, with the names changed:

```text title="Without the dot (illustrative, names changed)"
> nslookup example.com 8.8.8.8
Non-authoritative answer:
Name:    example.com.corp.example
Address:  198.51.100.80
```

A trailing dot means "this name is complete, don't add anything":

```text title="With the dot (real output)"
> nslookup example.com. 8.8.8.8
Server:  dns.google
Address:  8.8.8.8

Non-authoritative answer:
Name:    example.com
Addresses:  2606:4700:9a65:72db:f2ef:0:ef6b:ff98
          172.66.147.243
          104.20.23.154
```
</Step>
<Step title="Ask a second resolver, and compare">
Name the resolver at the end: `nslookup api.example.com. 8.8.8.8`, then `nslookup api.example.com. 1.1.1.1`. If your own resolver's answer differs from both, you've found your problem.
</Step>
<Step title="Read the TTL">
On Windows, PowerShell shows it directly:

```text title="Resolve-DnsName example.com -Type A (real output)"
Name        Type TTL IPAddress
----        ---- --- ---------
example.com    A 300 104.20.23.154
example.com    A 300 172.66.147.243
```

On macOS and Linux, `dig api.example.com` shows the TTL as the second column of the answer. `ipconfig /displaydns` lists what Windows itself has cached, each entry with its own **Time To Live**.
</Step>
<Step title="Check the hosts file">
Windows: `C:\Windows\System32\drivers\etc\hosts`. macOS and Linux: `/etc/hosts`. An old line there wins against every DNS server in the world, and only on your machine.
</Step>
<Step title="Clear the cache that matters">
- **Chrome:** open `chrome://net-internals/#dns` and press **Clear host cache**.
- **Windows:** `ipconfig /flushdns`.
- **macOS:** `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder`.

None of these clear your resolver's copy. For that, you wait for the TTL to run out, or ask a different resolver.
</Step>
<Step title="Moving a site? Lower the TTL first">
If the record's TTL is a day, caches may hold the old address for a day after you change it. So lower the TTL to a few minutes **a day or more before** the move, wait for the old TTL to pass, then switch. Afterwards, raise it again.
</Step>
</Steps>

## What developers often get wrong

**"DNS changes take 48 hours to propagate."** Nothing propagates. Old copies simply expire. The famous 48 hours is the TTL on the name-server records the root and `.com` hand out, so it matters when you move a domain to *different name servers*. Changing an address at your current DNS provider only waits for that record's own TTL, often a few minutes.

**"Flushing my DNS fixes it for everyone."** It clears only your own computer's copy. Your resolver, and everyone else's, keep theirs until the TTL runs out.

**"A name has one address."** Popular names often have several, for both IPv4 and IPv6. `example.com` had three when we asked.

**"TTL is how long a change takes."** It's how long one copy may be kept. A cache that refreshed just before your change keeps the old answer for the whole TTL; one that refreshes just after picks up the new answer at once.

**"`nslookup` shows exactly what the browser sees."** Not quite. The browser has its own cache, and `nslookup` can add a search suffix the browser doesn't. Use a trailing dot, and clear the browser's cache when you compare.

## Interview questions you should be able to answer

<Interview>
<Question q="What happens when you look up a domain name?">
The browser checks its own cache, then the operating system checks its cache and the hosts file. If nobody has a copy, the question goes to a recursive resolver, usually the internet provider's or a public one like 8.8.8.8. If the resolver has no copy either, it asks a root server, which points to the TLD servers (such as .com); they point to the domain's authoritative name server, which gives the real answer. Every answer comes with a TTL, and every step caches it on the way back, which is why most lookups are a single short round trip, or none at all.
</Question>
<Question q="What is a TTL, and how would you plan a DNS change for a server migration?">
The TTL is how many seconds any cache may keep an answer. Before a migration, lower the record's TTL to a few minutes, and do it at least one old-TTL ahead, so every cache has picked up the short TTL by the time you switch. Then change the record: caches move over within minutes. Keep the old server running for a while for anyone still on an old copy, then raise the TTL again.
</Question>
<Question q="Why do DNS changes seem to take up to 48 hours?">
Nothing propagates; cached copies expire. The 48 hours comes from the TTL of 172,800 seconds on the name-server records that the root and TLD servers hand out. That matters when you change which name servers a domain uses. A plain address change only waits for that record's own TTL, which is often minutes.
</Question>
<Question q="What's the difference between a recursive resolver and an authoritative name server?">
An authoritative name server holds a domain's real records and answers only for its own domains. A recursive resolver answers anyone's question about any name: it finds the answer by asking authoritative servers, then caches it for everyone who uses it. Your computer talks to a resolver; the resolver talks to authoritative servers.
</Question>
<Question q="A site works for you but not for a colleague on another network. How do you debug it?">
Compare the answers each of you gets: run nslookup with the name and a trailing dot, then against public resolvers such as 8.8.8.8 and 1.1.1.1. Differences point to a stale or wrong copy in one resolver, or split DNS (an internal resolver that knows different names). Check the TTL, the hosts file on the failing machine, and VPN or office DNS settings. Then confirm in DevTools whether the browser even got an address.
</Question>
<Question q="What's the difference between an A record and a CNAME?">
An A record maps a name straight to an IPv4 address (AAAA for IPv6). A CNAME says the name is an alias for another name, so the resolver looks that one up next, which adds a step. A CNAME can't share a name with other records, which is why you usually can't put one on the bare domain itself (example.com), only on names like www.example.com.
</Question>
<Question q="What is negative caching, and how can it bite you?">
When a name doesn't exist, resolvers cache that "no" for a time the domain sets in its SOA record. If anyone looked up a name just before you created it, their resolver keeps answering "doesn't exist" until that time passes. Testing a new record by asking a different resolver, or a fresh name, avoids the confusion.
</Question>
</Interview>
