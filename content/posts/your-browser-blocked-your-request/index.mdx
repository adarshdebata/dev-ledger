**You use it every day. But do you actually know what happens underneath?** Few errors are as common, or as misunderstood, as this one.

You build an <Term id="api">API</Term>. You test it in Postman, and it works: `200 OK`, with the data you expected. Then you call the same API from your website, and the browser shows a red error instead.

Same address. Same request. Same server. So why does one work and the other fail?

<Callout type="story" title="The short answer">
Your browser is protecting **you**, the person using it. Postman isn't a browser, so it doesn't need to. And here's the part most developers miss: **the request usually reached your server and ran.** The browser only refused to show your code the answer.
</Callout>

By the end of this article you'll know why that happens, how to read any CORS error, and how to fix it properly.

Look at three things:

1. **`net::ERR_FAILED 200 (OK)`.** This line contains a <Term id="status-code">status code</Term>: `200`, which means success. So the server *did* answer.
2. **"blocked by CORS policy".** The browser is the one blocking. Not your server, and not the network.
3. **`TypeError: Failed to fetch`.** This is all your JavaScript gets. No status, no <Term id="header">headers</Term>, no data. Your code can't even tell a CORS problem apart from a broken internet connection. That's on purpose, as you'll see.

So why does Postman work? Because Postman is not a browser. It doesn't run code from random websites while you're logged in to your bank. Neither does `curl`, and neither does one server calling another. That's the first big clue: **<Term id="cors">CORS</Term> is a browser feature.** It protects the person using the browser.

## The problem it solves: one browser, many websites

### What an origin is

Browsers keep websites apart using **<Term id="origin">origins</Term>**. An origin is made of three parts, and only three: the scheme (`http` or `https`), the host (the domain name) and the <Term id="port">port</Term>.

<UrlAnatomy />

Two addresses have the *same origin* only when all three parts match. The path (like `/orders`) and anything after `?` don't count. Try a few pairs:

<OriginCompare />

That `localhost:3000` versus `localhost:5173` pair causes more CORS errors than anything else. Your frontend runs on one port and your API on another, so the browser treats them as two different websites, even on the same laptop.

### Why the browser cares

Imagine you're logged in to your bank in one tab. In another tab, you open some random blog. That blog's JavaScript runs inside *your* browser, which also holds *your* bank <Term id="cookie">cookies</Term>.

Now imagine browsers had no rules. The blog's script could do this:

```js title="random-blog.js"
// Ask the bank for your accounts, sending your bank cookies along
const res = await fetch('https://bank.example/api/accounts', {
  credentials: 'include',
});
const accounts = await res.json(); // ...read your balances
// ...and send them to someone else
await fetch('https://collector.example/save', {
  method: 'POST',
  body: JSON.stringify(accounts),
});
```

The bank would see a normal request from a logged-in customer. It has no way to know you didn't make it. Only your browser knows the request came from a different website.

That's why browsers follow the **<Term id="same-origin-policy">same-origin policy</Term>**, a rule they've had since the 1990s:

- a web page **can send** requests to other websites (forms and images always could),
- but it **can't read the answers**, unless the other website allows it.

The same rule also protects things only your browser can reach, like your Wi-Fi router's settings page at `192.168.1.1`, or a dashboard on your office network.

<Callout type="story" title="Think of it like this">
The same-origin policy is a wall between websites. **CORS is a door in that wall.** It's how a server says "this other website may read my answers". CORS never makes anything *more* locked down; it only opens the door, and only as wide as the server chooses. So a "CORS error" really means: *the server didn't open the door for your website.*
</Callout>

## What's actually happening underneath

Let's slow the request down and watch every decision the browser makes.

### Step 1: the browser adds an `Origin` header

Your page at `https://app.example.com` calls `fetch('https://api.example.com/orders')`. The browser notices the two origins are different, so it adds a header you never wrote:

```http title="Request" {3}
GET /orders HTTP/1.1
Host: api.example.com
Origin: https://app.example.com
Accept: */*
```

JavaScript can't set or change `Origin`. It's a <Term id="forbidden-header">forbidden header</Term> that only the browser controls. That makes it trustworthy for the browser's own check, but only there. A tool like `curl` can send any `Origin` it likes, so `Origin` never proves who is calling.

### Step 2: the server answers, ideally with permission

If the API wants `app.example.com` to read the answer, it says so with a header in its <Term id="response">response</Term>:

```http title="Response" {3,4}
HTTP/1.1 200 OK
Content-Type: application/json
Access-Control-Allow-Origin: https://app.example.com
Vary: Origin
```

`Access-Control-Allow-Origin` holds exactly one origin, or `*` for "anyone". It can't hold a list. So servers keep their own <Term id="allowlist">allowlist</Term> and copy back whichever origin matches. When they do that, the `Vary: Origin` header tells <Term id="cache">caches</Term> that different websites get different answers. Remember that header; it comes back later.

### Step 3: the answer arrives first, then the browser decides

This is the part that surprises people. For a normal `GET`, the browser doesn't ask permission first. It sends the request. The server does the work and replies. *Only then* does the browser check `Access-Control-Allow-Origin`. Press play and watch:

### Simple requests and preflight requests

Wait. If the browser sends first and checks later, couldn't a bad website send a `DELETE` to your bank and simply ignore the answer? This is where the **<Term id="preflight">preflight</Term>** comes in.

Long before CORS existed, web pages could already send some requests to other websites. An HTML `<form>` could send a `POST` anywhere, and an `<img>` tag could send a `GET`. Servers had lived with that for years. So CORS was designed to allow, without asking first, **only what a form could already send**. These are called **<Term id="simple-request">simple requests</Term>**:

- the method is `GET`, `HEAD` or `POST`,
- you only add basic headers, such as `Accept`, `Accept-Language`, `Content-Language` and `Content-Type`,
- and `Content-Type`, if you set it, is one of the three values a form can send: `application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain`.

Anything else needs permission first: a `PUT`, `PATCH` or `DELETE`, a JSON body (`Content-Type: application/json`), an `Authorization` header, or any custom header like `X-Request-Id`. For these, the browser holds your request back and first sends a small `OPTIONS` request to ask: "may I?"

<Predict

Only the JSON `POST`. `application/json` is not one of the three types an HTML form can send, so the browser asks first. A form-style `POST` is something any `<form>` could already do. And cookies on their own don't cause a preflight; they change what the *answer* must contain, as you'll see below.
</Predict>

### The preflight, line by line

Say your frontend updates an order. It sends JSON and a login <Term id="token">token</Term>:

```js title="client.js"
await fetch('https://api.example.com/orders/1042', {
  method: 'PUT',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': `Bearer ${token}`,
  },
  body: JSON.stringify({ qty: 2 }),
});
```

Before that `PUT` leaves, the browser sends this by itself:

```http title="Preflight request, sent by the browser" {1,3-5}
OPTIONS /orders/1042 HTTP/1.1
Host: api.example.com
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: authorization,content-type
```

It's a question: *"A page from `https://app.example.com` wants to send a `PUT` with the `authorization` and `content-type` headers. Is that OK?"* Two details are easy to miss. The header names are lower-case and sorted. And the preflight carries **no cookies and no `Authorization` header**. It only asks; it doesn't do anything.

A server that agrees answers like this:

```http title="Preflight response" {2-5}
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 7200
Vary: Origin
```

The browser then checks four things, in order:

1. The status is a success (2xx).
2. `Allow-Origin` matches the page's origin.
3. `PUT` is listed in `Allow-Methods`. (`GET`, `HEAD` and `POST` are always allowed.)
4. Every extra header the request wants is listed in `Allow-Headers`. Upper or lower case doesn't matter.

Only if all four pass does the real request go out. And its response must *also* carry `Access-Control-Allow-Origin`.

### Credentials: when cookies join in

By default, `fetch()` only sends cookies to your own website. To send them to *another* website, you have to ask for it:

```js
// with axios: { withCredentials: true }
fetch('https://api.example.com/me', { credentials: 'include' });
```

That one setting makes the browser much stricter about the answer. With <Term id="credentials">credentials</Term>, the server must send:

- `Access-Control-Allow-Credentials: true`, with exactly that value, and
- an **exact** `Access-Control-Allow-Origin`. The <Term id="wildcard">wildcard</Term> `*` is not accepted.

Why so strict? Because `*` plus cookies is exactly the bank attack from earlier: *any* website could read *your* logged-in data. The browser enforces this rule itself, so one careless header can't open that hole. With credentials, `*` also stops meaning "anything" in `Allow-Methods`, `Allow-Headers` and `Expose-Headers`. And with or without credentials, `*` in `Allow-Headers` never covers `Authorization`. You always have to list that one by name.

<Callout type="danger" title="The classic CORS security hole">
Some servers "fix" the wildcard error by copying whatever `Origin` arrives straight into `Access-Control-Allow-Origin`, together with `Allow-Credentials: true`. The browser can no longer tell anything is wrong, and now *every website on the internet* can read your users' private data. Always compare against a fixed allowlist. And never allow the origin `null`: sandboxed iframes and local files send `Origin: null`, and an attacker can fake that too.
</Callout>

Cookies also have their own rules. In Chrome, a cookie without a `SameSite` setting is treated as `SameSite=Lax`, and Lax cookies are not sent with a `fetch()` to a different *site*, whatever CORS says. `app.example.com` and `api.example.com` are different origins but the same *site*, because both end in `example.com`. So normal cookies still travel between them. A frontend on a completely different domain needs the API's cookie to be set with `SameSite=None; Secure`.

### Reading headers: `Access-Control-Expose-Headers`

Even when the check passes, JavaScript can only read a short list of response headers: `Cache-Control`, `Content-Language`, `Content-Length`, `Content-Type`, `Expires`, `Last-Modified` and `Pragma`. Anything else, such as your `X-Request-Id` or a rate-limit counter, reads as `null`, unless the server lists it:

```http
Access-Control-Expose-Headers: X-Request-Id, X-RateLimit-Remaining
```

If you've ever seen a header clearly in the Network tab while `res.headers.get()` returned `null`, this is why.

### Remembering the preflight with `Max-Age`

A preflight adds an extra round trip before the real request. On a slow mobile network, that can cost a few hundred milliseconds. <Term id="max-age">`Access-Control-Max-Age`</Term> lets the browser remember a successful preflight for a while:

- With no `Max-Age` header, the browser remembers it for just **5 seconds**.
- Chrome remembers it for at most **7200 seconds** (2 hours), and Firefox for at most 86,400 (24 hours). Bigger values are quietly cut down.
- The browser remembers it per origin, per **exact URL** and per credentials setting. So `PUT /orders/1` and `PUT /orders/2` each need their own preflight. If your API puts IDs in its URLs, that adds up quickly.

In Chrome's Network tab, a preflight shows up as its own row of type `preflight`, right next to the request it asked about.

### All the headers on one screen

| Header | Sent with | What it says, in plain words |
| --- | --- | --- |
| `Origin` | every CORS request | "This request comes from this website." Set by the browser, never by your code. |
| `Access-Control-Request-Method` | preflight request | "The real request will use this method." |
| `Access-Control-Request-Headers` | preflight request | "The real request will send these extra headers." |
| `Access-Control-Allow-Origin` | response | "This website may read my answer." One origin, or `*`. |
| `Access-Control-Allow-Credentials` | response | "You may read this even though cookies were sent." |
| `Access-Control-Allow-Methods` | preflight response | "These methods are allowed." |
| `Access-Control-Allow-Headers` | preflight response | "These extra headers are allowed." |
| `Access-Control-Expose-Headers` | response | "JavaScript may also read these headers." |
| `Access-Control-Max-Age` | preflight response | "Remember this answer for this many seconds." |
| `Vary: Origin` | response | "Caches: different websites get different answers." |

Let's go back to the line that started all this: `net::ERR_FAILED 200 (OK)`.

So remember: **blocked is not the same as "didn't happen"**. Preflight requests are a little different. If the *preflight* fails, the browser never sends the real request, so nothing runs except the `OPTIONS` check. But if the preflight passes and the *real* answer comes back without CORS headers (like the 500 error below), then the request did run.

<Callout type="insight" title="The same lesson shows up everywhere">
"I got an error, so nothing happened" is one of the most expensive mistakes in backend work. A CORS block, a timeout and a dropped connection all look alike: the client lost the *answer*, not necessarily the *action*. Later in this blog we'll see why a timeout doesn't mean the operation failed, and why payment APIs use idempotency keys to make retries <Term id="idempotent">safe to repeat</Term>. It's also why CORS can't protect you from <Term id="csrf">CSRF</Term>: a form post from another site is a simple request, so it runs.
</Callout>

## Setting it up properly in Express

In Express, most people use the [`cors` package](https://github.com/expressjs/cors). Below is a good setup for an API that a browser app calls with cookies or tokens. Next to it is the same thing written by hand, so you can see there's no magic:

<CodeTabs labels={["Express + cors", "Raw headers"]}>

```js title="server.js"
import express from 'express';
import cors from 'cors';

const app = express();

const corsOptions = {
  // Exact origins only. No trailing slash: an Origin header never has a path.
  origin: ['https://app.example.com', 'http://localhost:5173'],
  credentials: true, // Access-Control-Allow-Credentials: true
  methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization', 'X-Request-Id'],
  exposedHeaders: ['X-Request-Id'],
  maxAge: 7200, // remember preflights for 2 hours, Chrome's limit
};

// First, before auth, body parsers and routes: every response gets the headers,
// and preflights are answered (204) before anything else can reject them.
app.use(cors(corsOptions));

app.use(express.json());
app.use(requireAuth);
app.use('/orders', ordersRouter);
```

```js title="server.js"
const ALLOWED_ORIGINS = new Set(['https://app.example.com', 'http://localhost:5173']);

app.use((req, res, next) => {
  const origin = req.headers.origin;
  res.vary('Origin'); // the response depends on Origin, so tell caches

  if (origin && ALLOWED_ORIGINS.has(origin)) {
    res.setHeader('Access-Control-Allow-Origin', origin);
    res.setHeader('Access-Control-Allow-Credentials', 'true');
    res.setHeader('Access-Control-Expose-Headers', 'X-Request-Id');
  }

  // A preflight is an OPTIONS request that carries Access-Control-Request-Method.
  if (req.method === 'OPTIONS' && req.headers['access-control-request-method']) {
    if (origin && ALLOWED_ORIGINS.has(origin)) {
      res.setHeader('Access-Control-Allow-Methods', 'GET, POST, PUT, PATCH, DELETE');
      res.setHeader('Access-Control-Allow-Headers', 'Content-Type, Authorization, X-Request-Id');
      res.setHeader('Access-Control-Max-Age', '7200');
    }
    return res.sendStatus(204); // answer it here; never let it reach auth
  }

  next();
});
```

</CodeTabs>

A few choices in that code are deliberate:

- **Order matters.** Put `cors()` first. Anything that runs before it, such as a login check, a rate limiter or `express.json()` rejecting bad JSON, sends responses without CORS headers. In the browser, those show up as confusing CORS errors.
- **The middleware never blocks anything.** Look at the hand-written version again: an unknown origin still gets a normal response, just without `Access-Control-Allow-Origin`. CORS <Term id="middleware">middleware</Term> only *adds headers*. The browser does the blocking, which is why `curl` gets through every time.
- **`Vary: Origin`.** The `cors` package adds it for you when the allowed origin depends on the request. If you write it by hand, you have to remember it.
- **Saying no quietly.** If you pass a function as `origin`, call `callback(null, false)` for websites you don't allow. If you pass an `Error` instead, your error handler sends a 500 without CORS headers, and the browser reports a CORS error for what is really your own error handler.

And on the client:

```js title="client.js"
const res = await fetch('https://api.example.com/orders', {
  method: 'POST',
  credentials: 'include', // only for cookies; a token in a header doesn't need it
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ item: 'book', qty: 1 }),
});
```

<Callout type="tip" title="The best CORS setup is no CORS at all">
If your frontend and API can share one origin, CORS disappears completely, and so does the extra preflight trip. In development, let your dev server forward API calls (Vite's `server.proxy`, or `rewrites` in Next.js), so the browser only ever talks to `localhost:5173`. In production, a reverse <Term id="proxy">proxy</Term> can serve the API under the same address as the app, like `https://app.example.com/api`. How a reverse proxy works gets its own article in Series 2.
</Callout>

## What breaks when it fails

Many of the hardest CORS bugs have nothing to do with your `cors()` settings. They come from responses that never pass through your CORS code at all. In the console they all look the same, so learn to read the Network tab instead.

### The 500 error that looks like a CORS error

Your code crashes, and the error is handled somewhere that doesn't add CORS headers. That could be an error handler that runs before `cors()`, a crashed process behind a proxy, a 502 or 504 from a load balancer, or a 413 "too large" from Nginx. The browser gets an error response without `Access-Control-Allow-Origin`, so the console says *CORS*, and your JavaScript only sees a `TypeError`. The Network tab shows the real status code.

If your CORS headers are added by Nginx, there's a classic trap: `add_header` only applies to successful responses (2xx and 3xx) unless you add the word `always`.

```nginx title="nginx.conf" {9,10}
map $http_origin $cors_origin {
    default                   "";
    "https://app.example.com" $http_origin;
}

server {
    location /api/ {
        proxy_pass http://app:3000;
        add_header Access-Control-Allow-Origin $cors_origin always;  # "always": 4xx and 5xx too
        add_header Vary Origin always;
    }
}
```

Let only one layer handle CORS. If Nginx and your app both add `Access-Control-Allow-Origin`, Chrome rejects the response with *"The 'Access-Control-Allow-Origin' header contains multiple values …, but only one is allowed."*

### Login middleware answering `OPTIONS` with 401

Preflights carry no cookies and no `Authorization` header, on purpose. If your <Term id="authentication">authentication</Term> check runs before your CORS code, it sees a request with no login and answers `401`. Depending on whether CORS headers were added first, the browser shows one of these:

```text title="Chrome console, one of these" wrap
Response to preflight request doesn't pass access control check: It does not have HTTP ok status.
Response to preflight request doesn't pass access control check: No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

Either way, the real request is never sent. The fix is the order: handle CORS (and answer preflights) before authentication, as in the Express example. If a gateway does authentication for you, make sure it lets `OPTIONS` requests through without a login.

### Proxies and CDNs that change your headers

Anything between the browser and your app can break CORS, even when your code is correct:

- **A proxy or gateway answers `OPTIONS` itself**, often with `405 Method Not Allowed`, so your CORS code never sees the preflight.
- **Headers get removed.** A proxy that only passes on headers it knows about drops every `Access-Control-*` header.
- **A <Term id="cdn">CDN</Term> gives one website's answer to another.** The first visitor comes from `admin.example.com` and gets `Access-Control-Allow-Origin: https://admin.example.com`. The CDN saves that answer by URL only. The next visitor comes from `app.example.com`, gets the saved copy, and sees a CORS error. It works when the cache is empty and fails when it's full: the most confusing kind of on-and-off bug. Adding <Term id="vary">`Vary: Origin`</Term> (or adding `Origin` to the cache key) fixes it.

### Redirects during the preflight

A preflight must get a success (2xx) answer. If `OPTIONS /orders` gets a <Term id="redirect">redirect</Term> instead, for example from `http://` to `https://`, from `/orders` to `/orders/`, or to a `/login` page, Chrome stops:

```text title="Chrome console" wrap
Response to preflight request doesn't pass access control check: Redirect is not allowed for a preflight request.
```

The fix: call the final URL directly, with the right scheme and the right trailing slash.

### A 60-second debugging routine

<Steps>
<Step title="Open the Network tab, not the console">
Find the failing request. Is there a row of type `preflight` next to it? That tells you whether the problem is the preflight or the real answer.
</Step>
<Step title="Read the status code first">
If the preflight isn't a 2xx, or the real request got a 4xx or 5xx, the problem is *whatever produced that status*, such as a login check, a crash or a proxy, not your CORS settings.
</Step>
<Step title="Compare the headers letter by letter">
`Access-Control-Allow-Origin` must match the request's `Origin` exactly: same scheme, host and port, and no slash at the end. With cookies, it can't be `*`, and `Access-Control-Allow-Credentials` must be `true`.
</Step>
<Step title="Repeat it without a browser">
`curl` shows exactly what the server sends, with nothing hidden:

```bash
curl -i -X OPTIONS https://api.example.com/orders \
  -H "Origin: https://app.example.com" \
  -H "Access-Control-Request-Method: PUT" \
  -H "Access-Control-Request-Headers: authorization,content-type"
```
</Step>
<Step title="Check every hop">
If your app's own answer is right but the browser's isn't, something in between (a CDN, a gateway, Nginx) is changing it. Try a request that skips each layer, one at a time.
</Step>
</Steps>

## What developers often get wrong

**"CORS protects my API."** It doesn't. It protects *people using browsers* from pages that would read data with their cookies. `curl`, Postman, scripts and other servers ignore CORS completely. Your API still needs proper login and permission checks on every route. CORS is not a server-to-server security tool.

**"Checking the `Origin` header is like a login check."** Outside a browser, anyone can send any `Origin` they like. It's a hint that the *browser* enforces, never proof of who is calling.

**"CORS stops CSRF."** CORS stops another website from *reading* the answer, not from *sending* the request. A form post from another site is a simple request: it reaches your server with the user's cookies, and it runs. Stopping that needs different tools, which is exactly what the next article covers.

**"The browser blocked my request."** It blocked the *answer*. For simple requests, and for any real request after a passing preflight, the server has already done the work. Treat a CORS failure on a write like a timeout: the action may well have happened.

**"A 'disable CORS' extension fixes it."** These extensions (and `--disable-web-security`) only switch the check off *in your own browser*. Every one of your users still gets the error. And while it's switched off, the sites you visit lose the protection the check exists to give. Use them to confirm what's wrong, never as the fix.

**"`mode: 'no-cors'` makes the error go away."** It does, by giving you an <Term id="opaque-response">opaque response</Term>: status `0`, no headers, an empty body. You can't read anything, and you're limited to simple requests. It has a few uses, like fire-and-forget pings, but calling your API isn't one of them.

**"`Access-Control-Allow-Origin: *` is always dangerous."** For truly public data without cookies, such as a public API, web fonts or open datasets, `*` is exactly right. The browser already refuses it whenever cookies are involved. The real dangers are copying back any origin *together with* credentials, and using `*` on internal services that only your colleagues' browsers can reach.
